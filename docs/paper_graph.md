# 数模论文状态图流水线（v2）

`backend/ai_system/graph/` 用 LangGraph 状态图替换原来的单个 ReAct 主循环（MainAgent + ReviewAgent 续写）。
设置 `AI_PIPELINE=v2` 后，无模板的 Markdown 任务走这条流水线，其余情况仍用 MainAgent。

## 流程

```
analyze ─┬─(AI_CONFIRM_MODELS=1)─Send×N──▶ design ──▶ confirm ─┬─(有修改意见)──▶ design
         │                                                     └─(通过)──▶ solve
         └─(默认，按需设计)──────────────────────────────────────────────▶ solve（设计 → explore → 正式求解 → 审查）

solve（按依赖分批并行）──▶ reconcile ──▶ write ──▶ validate ─┬─▶ repair ──▶ validate
                                                            └─▶ render
```

不需要人工确认方案时，设计放进各子问题的求解分支里按需进行：Q1 设计完立即开始求解，不用等其他子问题的设计；
Q2 轮到时 Q1 已经求解完，候选方案的生成请求里带着 Q1 的实际结论和登记结果（滚动规划）。
需要人工确认时仍然先并行设计全部子问题，再一次性交给用户确认。

| 阶段 | 做什么 | 关键设计 |
|---|---|---|
| analyze | 固定代码读取 `data/`、`attachment/` 下的表格生成数据概览；模型拆出子问题 Q1…Qn 及依赖关系；再用确定性规则补齐模型漏填的字段（问题描述里提到的前序子问题算依赖，标题是备忘录/信函的记为写作类，写作类没有依赖时依赖全部计算类） | 数据概览不经过模型，每题一致；依赖不靠模型自觉填写 |
| design | 每个子问题并行：从方法库（`methods.py`，25 种常用数模方法）挑 2~4 种 → 生成 n 个候选方案 → 判分器按"贴题 / 可行 / 数据利用 / 严谨"四项打分，选期望分最高的 | actor-critic；每个候选一次请求评完四项、候选之间并行（有 Jev key 用 Jev，否则用 LLM 结构化打分）。所有候选塞进一次请求时，模型会给各候选打出相同分数 |
| confirm | 可选的人工确认点（`AI_CONFIRM_MODELS=1`）：`interrupt` 把方案发给用户，回复"确认"继续，其他回复作为修改意见重新设计 | checkpoint 落盘，用户隔多久回复都能接着跑 |
| solve · explore | 前两名评审总分差距不超过 2 分、不是假设检验类子问题（"是否随机""是否存在"，不同检验的统计量不能比高低）、且能定出统一数值指标时，评分最高的 k 个候选（默认 2）先在数据上试跑（否则直接按评审选择求解，省下试跑成本）：先定统一验证协议（同一指标、同一划分、同一基线），各候选开独立内核并行跑一个短循环（默认 12 步），按协议汇报指标；指标要通过与结果登记相同的核对才参与比较。有可比指标按指标选（1% 内打平用评审分），没有统一指标时按 critic 对执行证据的评分选 | 借鉴 AIDE / MLE-bench 的执行驱动搜索；胜出分支的内核和对话历史整体晋升为正式求解，探索的计算不浪费；记录在 `designs[Qn].exploration` |
| solve | 写作类子问题（备忘录、建议信等，analyze 标为 `kind=writing`）不设计方案、不开内核，写作时直接依据前序结论和登记结果撰写；计算类按依赖关系分批并行，每个子问题一个 CodeAct 循环 + 独立的持久 Python 内核；交报告后由审查模型检查数据范围、泄漏、过拟合、指标选择、结论是否被支持，必须修正的问题交回同一循环返工（默认 1 轮） | 变量跨步保留；早期代码和输出按 10 步一块压缩（`compaction.py`），至少保留最近 6 步原文，块内前缀不变以命中缓存 |
| reconcile | 各子问题报告的主要结论登记为结论节点（陈述 + 证据强度 显著/倾向/不显著 + 指向登记结果的证据）；审查模型通读结论表，找出跨子问题矛盾和强度与证据不符的结论，给出统一口径 | 结论图：登记表从"数字可追溯"扩展到"结论可追溯"；统一口径写进 `.system/consistency.json` |
| write | 先并行写各子问题的建模求解章节，再写重述/分析/假设/符号/灵敏度/评价，最后写摘要 | 写作模型只看到结果登记表，数字只能写引用；每一节都带着结论表和统一口径 |
| validate / repair | 代码校验：章节缺失、未知引用、正文出现未登记的小数/百分数（公式里写成 `= 4.05` 的也算）、求解章节没引用结果或没插图；再用一次模型调用检查摘要、问题分析、灵敏度、评价是否与结论表一致；有问题的章节带着问题清单重写，最多 2 轮 | 数字校验不调模型；只修有问题的章节 |
| render | 引用替换为真实数值和图片，图按出现顺序编号，写出 `paper.md`；求解章节里只在行内提到（"见图1"）的图，插到首次提到它的段落之后；带引用的原稿留在 `.system/paper_raw.md` | 每个数字都能追溯到某次代码执行 |

## 标签置换对照（防泄漏）

审查模型抓不住所有泄漏。DeepSeek 跑 2024_C 时，Q1 用卡尔曼滤波"预测"当前这一分，但滤波值已经吸收了这一分的结果，LogLoss 从 0.68 降到 0.49，审查没有发现。所以预测效果另加一道确定性检查：

- 正式求解报告了预测效果（AUC、准确率、LogLoss、RMSE 等）时，必须在 `controls` 里给出标签置换对照：在构造特征之前把目标列打乱，其余流程不变，再算同一指标。真实值和打乱后的值都要能在执行输出里核对到。
- 打乱后仍保留真实提升（相对无信息水平）的一半以上，判为泄漏，作为必须修正的问题交回求解循环。返工后仍不通过的，写进局限，不能作为有效结论。
- 指标方向（越大越好还是越小越好）按指标名确定：LogLoss、RMSE、误差这类越小越好，AUC、准确率、F1 这类越大越好；认不出时才用模型填写的方向。2024_C 里模型给"LogLoss，越小越好"填了越大越好，两个方案都跑通时会选出更差的那个。
- 打乱的必须是原始结果列（如每一分的胜者），且在构造任何特征和标签之前打乱。只打乱训练集标签只能说明"模型没学到东西"，测不出特征里带了标签。实测中模型就这样做过：GBM 留出集 AUC 0.886，只打乱训练标签后是 0.627，判定通过；而它的"转折"标签正是由当期动量变号定义的，当期动量又被当成了特征。这类定义式泄漏另由审查清单检查。
- 探索阶段的 `ProbeReport.shuffled_value` 同样检查。不通过或缺失的指标不参与比较，避免泄漏的方案靠假指标胜出。
- 置换对照只能说明"比无信息水平好"，还要和最简单的有信息基线比（如只用发球方先验胜率）。DeepSeek 跑 2024_C 时，Q1 的滤波势头 LogLoss 优于无信息水平和置换对照，结论写成"势头携带预测信息"；但灵敏度分析里换任何噪声设置指标都不变，信息其实全来自发球方先验。现在 `controls` 要同时给出基线值，且基线不能等于无信息水平（v2h 的 Q1 拿常数先验胜率充当基线绕过了这项比较）；没超过基线的，第一轮审查要求把结论改成"相对基线没有额外提升"，并写进局限。
- 题目要求可视化的子问题，报告提交时一张图都没登记的要返工（v2h 的 Q1 没登记图，写作时编了一个不存在的 `{{F:F1}}`）。
- 打乱后的值恰好等于无信息水平（如 AUC 正好 0.5）的，视为填写的理论值，要求实际重算。假设检验类子问题不要求置换对照。
- 返工超出步数或出错时，保留返工前的报告，并把没完成的审查意见写进局限（v2h 的 Q2 登记了 20 项结果，返工超步数后整份报告曾被丢掉）。
- 模型审查返工之后，再多一轮只看确定性检查（有登记结果、结论数字是引用、对照齐全）。返工时模型常常补了计算却忘了改报告。

## 结论数字可追溯

求解报告的概要和主要结论里不能直接写小数或百分数（0.05、95% 这类约定常数除外），只能写登记结果的引用；直接写了的，和置换对照一样作为必须修正的问题交回求解循环，要求先 print、登记，再改成引用。
DeepSeek 跑 2024_C 时，Q2 只登记了验证集场数和置换次数两项，检验统计量 z=4.05、9.18 直接写在结论里，结论节点没有任何证据；写作时这些数又被放进公式 `$z = 4.05$`，躲过了正文数字校验（原来整段公式都不查）。

假设检验（自相关、游程等）不需要标签置换对照，检验的零分布本身就是对照。同一次运行里模型把置换对照硬套到 Ljung-Box 检验上，得出"置换后 z=9.18 仍显著"这种无法解释的结果。

## 代码参数清洗

网关的工具调用解析偶尔把 DeepSeek 的对话模板标记（`<｜DSML｜…>`、`</think>`）连同后面的文字一起塞进 `run_python` 的代码参数，导致 SyntaxError。一次运行 30 次执行里有 4 次这样浪费。现在执行前会截掉第一个模板标记及之后的内容。

## 结果登记表

求解时模型通过 `record_results([{name, value, run_id, unit, description}, ...])` 批量登记结果（一次调用登记一批，减少往返）。每条登记会检查：

- `run_id` 存在且执行成功；
- `value` 确实出现在这次执行的输出中（允许四舍五入到登记的位数、小数与百分数互换；至少两位有效数字才允许四舍五入）。

不满足就拒绝登记，模型必须先把结果 print 出来。模型常把 run_id 的随机后缀记错，这时到本问最近 8 次成功执行里找输出含这个值的那次登记，并告诉模型实际用的 run_id；值必须出现在真实输出里这一条不变。同一子问题的同名结果只保留一条：重复登记会复用原编号，返工后的新值原地更新，已写好的引用自动指向新值。图通过 `record_figure` 登记，并晋升到 `outputs/figures/F<n>.png`。
登记表存在 `.system/results.json`。

## 运行时文件

| 路径 | 内容 |
|---|---|
| `.system/graph.sqlite` | LangGraph checkpoint（AsyncSqliteSaver） |
| `.system/graph_thread.json` | 当前 thread 及状态（running / interrupted / done） |
| `.system/results.json` | 结果登记表（`results`）与结论节点（`claims`） |
| `.system/consistency.json` | 结论冲突与统一口径 |
| `.system/validation.json` | 最近一轮校验问题 |
| `plan.md` / `plan.json` | 各阶段进度，前端固定展示 |

结构化输出第一次用工具调用；参数不合 schema（如候选方案给了空列表）或模型没调用工具时，重试改为要纯文本 JSON 再校验。
候选方案的名称或思路是占位内容（`placeholder`、`...`、`待定` 等，DeepSeek 会把 schema 当模板原样填回）也算不合 schema。
analyze 拆出的"撰写完整论文"这类子问题会被删掉，论文本身就是流水线的产出。
求解报告提交时一项结果都没登记的，作为必须修正的问题交回求解循环（曾出现过按占位方案跑两段读数据代码就交报告）。
报告里的引用只能指向本子问题或其依赖登记的结果：v2g 的 Q3 一项都没登记，结论却写"验证集 AUC 为 {{R:R3}}"，R3 是 Q1 登记的验证集场数。返工后仍没有任何登记结果的，丢掉报告、按未完成交给写作。登记被拒会写进日志，方便看 trace。
某个子问题的候选方案多次生成失败时，不中止整篇，改用"求解时自行设计"的方案交给求解循环，失败原因记在 `designs[Qn].design_error`。

外部原因（网关故障、账号受限）让子问题求解失败时，`PaperGraphAgent.resume_failed()` 回到这些子问题开始求解之前的 checkpoint 重放，
先清掉它们失败时登记的结果；已完成的子问题不重跑。评测里对应 `python -m evals run --pipeline v2 --resume`。

## 2024_C 首轮评测发现的问题与对应改动

| 现象 | 改动 |
|---|---|
| 一题 56 分钟、534 万 token；输入 496 万中 90% 命中前缀缓存，但长循环会撑满上下文 | 按整块推进的上下文压缩（块内前缀不变，不破坏缓存）；评测记录 cache_read |
| Q1–Q3 只用了决赛一场数据；Q3 正样本 62.6% 时用 F1 显得偏高 | 结果审查节点；评审新增"数据利用"；求解提示要求全量数据、防泄漏、给基线 |
| Q3 模型用文字收尾、没交报告 | 提醒一次补交报告 |
| "68.7%%"、"-6.26 点 点"、"0.2320 p值"、公式内带单位 | 渲染去重单位、公式内只放数值；单位只填物理/计数单位 |
| 求解章节小标题与章节标题同级；备忘录被套成建模模板 | 小标题自动降级；按交付物文体写作 |

## 配置

| 环境变量 | 作用 |
|---|---|
| `AI_PIPELINE=v2` | 聊天接口启用状态图流水线 |
| `AI_CONFIRM_MODELS=1` | 建模方案需要用户确认 |
| `AI_EXPLORE_TOPK` | 求解前试跑几个候选方案（默认 2，设为 1 关闭探索） |
| `TYPESAFE_API_KEY` / `JEV_MODEL` | 用 Jev 评审候选方案（默认 `jev-1.14.0`） |

模型沿用工作的 brain / code / writing 配置：分析与设计用 brain，求解用 code，写作用 writing。
