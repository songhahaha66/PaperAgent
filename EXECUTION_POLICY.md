# Execution policy and compatibility

New research uses a versioned policy with `request_limit: null`. This is an absent/default cap, not a large substitute number. Every attempted model request and every returned input/output token count remains in the workspace SQLite database across pause, process restart and recovery. Missing token usage remains unknown; it is not estimated. Known token totals from earlier graph/editor traces are imported once when new request accounting starts.

`limit_source` distinguishes `default`, `explicit`, and `legacy`. An explicit positive setup limit is checked atomically before a request is sent. Existing unversioned settings and frozen request budgets retain their effective limits, usage and timeout. An existing project with an existing graph thread/checkpoint or research traces but no policy retains its previous effective 40-call limit. None of these compatibility reads starts or resumes a task. Newly initialized agents establish the new policy before writing a graph thread, so a new thread cannot accidentally be classified as legacy. Explicit confirmation choices and literature permissions remain in the existing setup API; a new runtime bootstrap does not override `AI_CONFIRM_MODELS`.

The homepage has one native, initially closed **Execution settings** disclosure. It preserves task/attachment/start controls, confirmation, literature permissions and optional explicit caps. It no longer presents a project-level 90-second timeout. Experience defaults and experience/profile modules are unchanged.

Model connections now have optional `timeout_seconds` (nullable, positive, at most 3600 seconds). A null connection value uses 600 seconds. Existing connection credentials, model IDs and providers are unchanged. The OpenAI-compatible parsed-chunk idle timeout follows this same connection value. Legacy or explicitly supplied project timeouts remain overrides for compatibility. Review leases renew while their process is alive; a long response alone is not evidence of failure or lack of research progress.

Model-service retries have one owner at the existing provider boundary. SDK retries are disabled before SDK clients are constructed, including clients instantiated with an internal retry override. Transient transport errors, timeouts, generic rate limits and server errors get at most three attempts with finite backoff. Authentication/permission failures, payment failures and recognized insufficient-quota codes stop immediately. A streamed reply is never automatically replayed after public, reasoning or tool-call content has been emitted. Retry logic encloses only model generation; it does not replay tools, nodes, exports or other workspace mutations. Structured-response repair remains separately bounded and cannot restart an exhausted provider retry loop; judge fallbacks propagate these stops too.

Durable failure records are keyed by the actual operation, model/connection fingerprint, request inputs and current input/policy fingerprints. Repeating the same failure three times blocks that operation across recovery. Different errors cannot erase earlier repetitions. Success clears that operation's failure history. Genuinely changed inputs or connection/policy settings use a different fingerprint; unrelated completed results are not invalidated. Connection authentication/quota blocks apply across operations for that connection. Only one-way fingerprints, sanitized categories, counts and safe messages are stored; no credential or prompt text is added to guard records. Older undifferentiated `provider_blocked` records remain historical service interruptions; a new probe requires a user action and uses the new bounded protection.

Recent work and research snapshots expose recorded reasons for manual pause, waiting for confirmation, service/authentication/quota errors, repeated failures and actual cap rejections. Unknown failures remain generic. Read-only recent-work projection does not migrate, execute or resume projects. Waiting for confirmation continues to require an explicit confirmation action; the backend rejects a generic resume action while confirmation is pending.

## Validation

Controlled OpenAI-compatible SDK transports cover 50 successful calls across two scopes, cumulative token usage, explicit/legacy caps, three-attempt transient faults, single-attempt authentication/quota faults, recovery guards, changed inputs, partial-stream interruption and historical token import. Existing graph, review, segmented-review, editing, budget and frontend workspace tests cover compatibility and retained results. No paid model calls are used.

A real local FastAPI/PostgreSQL API check creates only dedicated synthetic test accounts and unstarted work: default/explicit setup, confirmation and literature permissions, connection timeout updates without credential changes, and cap reasons through work lists and research snapshots. Chromium checks the homepage disclosure and retained choices against that API without opening an execution websocket. Raw SVG text and an isolated `1.` were not reproduced in the rendered homepage; no speculative display fix was added.

## Boundaries

This is not a general research-progress detector or a promise of exactly-once external provider generation. Failed attempts can consume upstream tokens even when usage is not returned. Existing per-task step/attempt limits, validation rules, code timeouts and experiment sub-budgets remain. Generic tool side effects are not automatically retried by this change. Provider-specific errors without recognizable status/codes are reported conservatively. No automatic model/provider switching, cost-pricing system, production deployment or existing-research execution is included.
